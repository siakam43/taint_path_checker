# taint-tree-checker 回调扇出追踪规则设计

日期：2026-08-19
状态：已批准

## 背景与问题

实测报告中出现以下表述：

> shmem_disp 通过 `(get_tcp_callback())[ver](...)` 间接调用回调函数（ver=0 时为 commu_amsm_recv_data，ver=2 时为 amf20_recv_data），污点经 `len` 与 `payload` 传播至树外。回调内部进一步通过 message_process 分发至大量业务注册回调，链路过深且数量众多，标注"无法逐一追踪"。

问题：间接调用的目标**实际上可确定**（已枚举出 ver=0/2 的目标函数，注册回调在代码中可搜索），AI 却以"数量众多、链路深"为由提前放弃追踪，导致漏报。

根因：SKILL.md 4.3 的"无法追踪"标注原本只允许"间接调用目标不明或源码缺失"两类情形，但文本未明确禁止"数量/深度"作为放弃理由，也没有给出"目标可确定但规模巨大"时的处理协议，AI 自行把工作量当作放弃依据。

## 目标

1. 明确：**目标可确定时不得放弃追踪**，"数量众多/链路深"不是"无法追踪"的合法理由。
2. 为"目标可确定但规模巨大"定义明确的追踪上限协议：深度 10 层、单分发点扇出 20 个回调；上限内必须完整追踪到终态，超出部分逐条列出。
3. 收紧"无法追踪"定义：仅限目标不可确定（且写明已尝试的搜索方式）或源码缺失。
4. 报告摘要要求逐回调/逐分支一行结论，禁止笼统表述。
5. 新增回调扇出测试夹具验证。

## 范围

- 只改 `taint-tree-checker/SKILL.md`。
- 新增夹具 `test_fixtures/callback_fanout/`。
- 不修改 taint-path-checker、taint-path-cleaner。

## SKILL.md 修改点

### 1. 4.3 "间接调用解析"行重写

现：

> - **间接调用解析**：通过函数指针赋值、回调注册点在 project_dir 中搜索确定目标函数；无法确定目标时该分支标注"无法追踪"并停止延伸，不臆造。

改为：

> - **间接调用解析**：通过函数指针赋值、回调注册点在 project_dir 中搜索确定目标函数。**目标可确定时必须继续追踪，不得以"数量众多/链路深"为由放弃**；规模超出上限时按下方"追踪上限"规则处理。仅当目标不可确定（穷尽搜索注册点/赋值点仍无果、运行时计算地址、外部模块无源码）或源码缺失时，该分支标注"无法追踪"并停止延伸，不臆造——**标注时必须在摘要写明已尝试的搜索方式**。

### 2. 4.3 新增"追踪上限"规则块（置于"落盘"条目之后）

> **追踪上限（目标可确定但规模巨大时）：**
>
> - **深度上限**：自入口函数起（入口为第 1 层），单条链最长追踪 10 层调用。第 10 层仍继续传播时停止延伸，摘要逐条列出链尾函数（函数名+行号+继续传播去向）。
> - **扇出上限**：单个分发点（函数表/注册回调集）最多追踪 20 个目标回调，按注册/初始化/表项顺序取前 20 个完整追踪；其余回调在摘要逐条列出（函数名+行号）。**每个分发点独立计算上限**（各自 20 个）。
> - **上限内必须完整追踪到终态**：上限之内的每个回调/分支，均须追踪至 4.3 完整性自检的终态之一（停止传播/无害消费/净化/危险使用点），不得中途以"复杂"为由跳过。
> - 上限仅用于规模巨大时的边界收敛，**不是常规偷懒借口**：扇出 ≤20、深度 ≤10 时必须全部逐一追踪。

### 3. 4.3 完整性自检收紧"无法追踪"定义

现：

> 标注"无法追踪"（间接调用目标不明或源码缺失，记录于摘要）

改为：

> 标注"无法追踪"（**仅限两类**：间接调用目标不可确定且已写明搜索方式；源码缺失。**"数量众多/链路深"不属于无法追踪**，规模超上限的按"追踪上限"规则在摘要逐条列出）

### 4. 报告摘要联动（7.3 分析摘要 / 7.4 分析情况）

两处模板的摘要部分各追加一句：

> 存在间接调用扇出时，摘要必须**逐回调/逐分支给出一行结论**（函数名：是否接收污点；追踪至何终态），禁止以"无法逐一追踪"等笼统表述代替。

### 5. 9.1 新增陷阱行 + 9.2 新增边缘情况行

9.1 思维陷阱表新增：

> | "回调太多/链路太深，标无法追踪吧" | 数量与深度不是无法追踪的理由。上限内必须完整追踪；超出上限的逐条列出（函数名+行号），不得笼统跳过 |

9.2 边缘情况表新增：

> | 间接调用扇出超出上限（深度>10 或单分发点回调>20） | 按"追踪上限"规则停止延伸，摘要逐条列出未深挖项（函数名+行号）；已追踪部分照常分析 |

### test.c（结构示意，实施时以实际行号为准）

```c
#include <stdint.h>

#define BUF_SIZE 64
#define CB_COUNT 4

static uint8_t g_buf[BUF_SIZE];
static void (*g_cbs[CB_COUNT])(uint32_t);   /* 回调表 */

static void cb_a(uint32_t idx) {            /* 回调1：校验完备 → 不应报 */
    if (idx >= BUF_SIZE) return;
    g_buf[idx] = 0xAA;
}

static void cb_b(uint32_t idx) {            /* 回调2：无校验 → 漏洞1 */
    g_buf[idx] = 0xBB;
}

static void cb_c(uint32_t idx) {            /* 回调3：传递污点到树外 helper → 漏洞2 */
    helper_write(idx);                      /* 深一层，验证补链 */
}

static void helper_write(uint32_t idx) {    /* 树外辅助函数 */
    g_buf[idx] = 0xCC;                      /* 无校验 */
}

static void cb_d(uint32_t idx) {            /* 回调4：不使用 idx */
    g_buf[0] = 0xDD;
}

void init_reg(void) {                       /* 注册点（供间接调用解析搜索） */
    g_cbs[0] = cb_a; g_cbs[1] = cb_b;
    g_cbs[2] = cb_c; g_cbs[3] = cb_d;
}

void func_disp(uint32_t ver, uint32_t idx)  /* 入口 */
{
    if (ver < CB_COUNT)
        g_cbs[ver](idx);                    /* 间接调用扇出，输入树在此中断 */
}
```

### 输入树与预期

- `fanout01.json`：顶层键 `func_disp$fanout01`，单条链、仅含 `func_disp` 一个节点——逼 AI 必须走 4.3 间接调用解析与修复。
- **预期报告**：发现 2 个漏洞——
  - 漏洞1：cb_b 中 `g_buf[idx]` 无校验（OOB Write）
  - 漏洞2：cb_c → helper_write（树外补链）中 `g_buf[idx]` 无校验（OOB Write）
  - 摘要中 4 个回调**各有一行结论**：cb_a 校验后净化；cb_b 到达危险使用点；cb_c 树外延伸至 helper_write 到达危险使用点；cb_d 形参接收污点但未使用、停止传播。
- **修复树** `fanout01_tree_fixed.json`：补入 4 条链——func_disp → cb_a（净化）、func_disp → cb_b（危险使用）、func_disp → cb_c → helper_write（危险使用）、func_disp → cb_d（污点停止传播）。cb_a/cb_d 补链依据"污点驱动"（实参含污点即计入）。
- **基线验证（RED）**：用当前技能对夹具运行，预期 AI 面对 4 回调扇出标注"无法逐一追踪"而漏报全部或部分漏洞，记录基线证据。
- 深 10/扇出 20 的上限本夹具不触发（规模小），上限规则的正确性靠规则文本审查保证；夹具验证的是"扇出时必须逐一枚举追踪、不得放弃"。

## 验证方式

1. 基线（RED）：当前技能跑 `fanout01.json`，记录漏报与放弃理由。
2. 修改 SKILL.md 后重跑（GREEN）：核对 2 个漏洞 ID、摘要 4 行逐回调结论、修复树 4 条链、无"无法逐一追踪"字样。
3. 回归：insufficient_check、tree_test、tree_repair 三个既有夹具重跑比对（忽略分析时间与措辞差异），漏洞 ID 与判定不得变化。

## 非目标

- 不修改"仅污点驱动"防路径爆炸规则（回调未接收污点时不补链的规则保持不变）。
- 不引入两遍法（先浅扫后深挖）——上限内一律完整追踪，防止 AI 在简单场景偷懒浅扫。
- 不改变漏洞上报格式与门禁三问。
- 上限数值（10/20）作为明确常量写入技能文本，不设计为可配置参数。
